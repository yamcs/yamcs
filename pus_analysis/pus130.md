# PUS ST[130] — Telemetry management

The simulator follows the Telemetry Management specification for mode transitions, event
overlays, and pass management. The wire definitions are in the active XTCE MDB. The example
loads [pus130.xml](../examples/pus/src/main/yamcs/mdb/pus130.xml).

| TC subtypes | Behavior | TM reports |
|---|---|---|
| 1, 2, 3 | Enter timed Beacon mode, enter NTM, and report the current mode | 4 |
| 5, 6, 7 | Add, delete, and report SIDs in the STM, Beacon, and CTM tables | 8 |
| 9–13, 15 | Edit, enable, disable, and report event overlays | 14, 16 |
| 17 | Report the source mask and resolved generation, store gate, and TX claims | 18 |
| 19, 20, 21, 23 | Start a manual or automatic pass, report pass state, and abort a dump | 22 |

For ST[130] TM, the four secondary-header spare bytes carry the one-based page number and total
pages as consecutive big-endian unsigned 16-bit integers. TC fields at the same position are zero.
For multi-page reports each page has its own application-data entry count. The current XTCE
profile uses 8-bit slot IDs in TC[130,20] and TM[130,22].

## Collection and forwarding

The STM table claims storage. Beacon and CTM table entries claim transmission in their
respective modes. An enabled overlay claims generation and storage after its event fires and
adds a transmission claim during CTM. Its timeout starts when the event fires again and ends when
the timer expires or the overlay is disabled. The ST[130] source mask assigns bits 0, 1, 2, and 3
to STM, Beacon, CTM, and active overlays respectively.

The simulator applies generation claims to ST[03] and checks ST[130] storage and transmission
policy before using the ST[15] storage selection and ST[14] forwarding rules. At startup, without
configured tables or active overlays, the existing ST[03] periodic entries drive reporting.
STM entries can be generated and stored during Beacon or CTM alongside the active mode's entries.

## Passes and dump slots

A pass enters CTM and ends at the LOS deadline. For an automatic pass, X delays the start of the
dump and Y reserves time before LOS. Slots execute in request order, bounded by the dump window
and each slot's allotted duration. Packet-store slots use ST[15] open retrieval and its existing
cursor. Payload-data slot ID 1 represents a synthetic payload slot and simulates progression for
the allotted duration. The pass report shows
the current slot and per-slot completion flags. Aborting a dump releases the slot and stops the
remaining work while the CTM pass continues to LOS.

Tests exercise mode transitions, atomic table edits, page metadata, timed overlay claims, and
dump cancellation through simulator command dispatch.
